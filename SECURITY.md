# Security Considerations

## Network
- Only the ALB's security group accepts inbound traffic from `0.0.0.0/0`, and
  only on 80/443. Application tasks and the database have no public IPs and
  no direct internet-facing security group rules.
- Security group rules chain off each other (ALB -> app -> db) instead of
  CIDR ranges, so the trust boundary is explicit and self-documenting.
- VPC Flow Logs are enabled and shipped to CloudWatch Logs for network-level
  audit and incident investigation.
- No SSH/RDP ports are opened anywhere. Break-glass access to ECS tasks
  should go through `aws ecs execute-command` (ECS Exec) over SSM, not SSH.

## Identity & access
- CI/CD authenticates to AWS via GitHub's OIDC provider assuming a
  short-lived IAM role (`aws-actions/configure-aws-credentials` with
  `role-to-assume`) — no long-lived AWS access keys are stored as GitHub
  secrets.
- ECS uses two distinct IAM roles per the standard split: an **execution
  role** (what ECS needs — pull image, write logs, read the DB secret) and a
  **task role** (what the running application is allowed to do — currently
  scoped to CloudWatch metrics/logs only). Neither role is broader than the
  service actually needs.
- Production deployments require a manual approval from a designated
  reviewer via a GitHub Environment protection rule, separate from the
  staging auto-deploy path.

## Secrets management
- The RDS master password is generated by Terraform (`random_password`),
  stored exclusively in **AWS Secrets Manager**, and injected into the ECS
  task at container start via the task definition's `secrets` block. It is
  never present in `terraform.tfvars`, CI/CD logs, the container image, or
  application source.
- `terraform.tfvars` (real values) is git-ignored; only
  `terraform.tfvars.example` with placeholder/non-sensitive defaults is
  committed.
- Application-level secrets used by CI/CD (Slack webhook, SMTP credentials,
  AWS role ARNs) are stored as GitHub Actions encrypted secrets, scoped per
  environment where possible.

## Data protection
- RDS storage is encrypted at rest (`storage_encrypted = true`).
- The ALB access-log S3 bucket blocks all public access, is encrypted at
  rest, and enforces a lifecycle policy that expires logs after 90 days.
- RDS is not publicly accessible (`publicly_accessible = false`) and lives
  in a private subnet tier with no route to the internet.

## Vulnerability management
- `npm audit` and Trivy filesystem scanning run on every PR against
  application dependencies.
- Trivy also scans the built container image for CRITICAL/HIGH CVEs before
  it's allowed to merge, and again (CRITICAL only, blocking) before it's
  pushed to ECR in the CD pipeline.
- ECR has `scan_on_push` enabled for a second, registry-side scan of every
  image.
- `tfsec` scans the Terraform for common IaC misconfigurations on every PR
  touching `terraform/`.

## Application security
- The container runs as a non-root user (`appuser`) in a minimal Alpine
  base image, built via a multi-stage Dockerfile so build tooling and dev
  dependencies never ship in the runtime image.
- ECS image tags are immutable (`image_tag_mutability = "IMMUTABLE"`) so a
  deployed tag can't be silently overwritten.

## Reporting a vulnerability
If you find a security issue in this repository, please open a private
security advisory (GitHub Security tab) rather than a public issue.
