## Key decisions

**ECS Fargate over EC2/EKS.** The brief allows EC2, ECS, or EKS. Fargate was
chosen because: no EC2 fleet to patch or manage, it scales down to zero
operational overhead for cluster capacity, and it's the simplest path to a
container-based deployment that still exercises everything the assignment
asks for (task definitions, service autoscaling, rolling deployments,
circuit-breaker rollback). EKS would be reasonable at higher team/cluster
complexity, but is overkill for a single service; swapping in an EKS module
later doesn't require changing the VPC, RDS, ALB, or CI/CD pipeline
structure.

**Three-tier subnet layout.** Public subnets hold only the ALB and NAT
gateways — nothing with application code or data ever gets a public IP.
Application tasks run in private subnets and reach the internet (for image
pulls, AWS API calls) only via NAT. The database sits in its own private
subnet tier with a security group that accepts traffic *only* from the app
tier's security group, not from a CIDR range — so adding/removing app
instances never requires touching the DB security group.

**Security groups reference each other, not CIDRs.** `alb` allows the
internet on 80/443; `app` allows only `alb`'s security group on the
container port; `db` allows only `app`'s security group on 5432. This means
the network topology self-documents: you can read the trust relationships
directly from `terraform/security_groups.tf` without cross-referencing IP
ranges.

**State management.** Terraform state lives in a versioned, encrypted S3
bucket with DynamoDB-based state locking (`terraform/versions.tf`). The
bucket/table are intentionally *not* created by this same Terraform config
(a backend can't safely manage itself) — they're bootstrapped once via the
AWS CLI commands documented inline. Each environment (staging/production)
uses a separate state key via `backend-<env>.hcl`, so a mistake in one
environment's plan can't touch the other's state.

**Secrets never touch source control or CI logs.** The RDS master password
is generated by Terraform's `random_password` resource, stored only in AWS
Secrets Manager, and referenced by ARN in the ECS task definition's
`secrets` block — ECS injects it as an environment variable at container
start. It is never written to `terraform.tfvars`, never printed in a
`terraform plan`/`apply` diff as plaintext (Terraform marks it sensitive),
and never baked into the container image.

**Deployment strategy.** The CD pipeline builds one image per commit to
`main`, scans it, pushes it to ECR, then does a task-definition revision +
`ecs update-service --force-new-deployment` rolling deploy. ECS's built-in
deployment circuit breaker automatically rolls back a bad deployment if the
new tasks fail to reach a healthy state. Production is gated behind a
GitHub Environment with required reviewers — the exact "manual approval
step" called for in the brief — so the same reviewed, scanned image that
passed staging is what gets promoted, with no separate rebuild.

## Notifications

CloudWatch alarms fan into a single SNS topic (`terraform/monitoring.tf`).
Two ways to route that to chat/email:
1. Subscribe an email address directly (`alarm_sns_topic_email` variable).
2. Add an `AWS Chatbot` Slack integration subscribed to the same SNS topic
   for real-time Slack alerts on infra/app/DB thresholds.

Pipeline failures (CI and CD) post to Slack via an incoming webhook
(`SLACK_WEBHOOK_URL` secret) and optionally email via SMTP — see the
`notify-on-failure` / `notify` jobs in `.github/workflows/ci.yml` and
`cd.yml`.
